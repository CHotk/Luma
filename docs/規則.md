## 零、整體 UX 原則

不管做哪個功能，都要以「使用者不用想就知道怎麼用」為標準
（2026-09-23 使用者明確要求：整體 UX 要很直覺好用）。具體來說：

- **常用動作不能被少用動作埋掉。** 一排頂部列擠 4、5 顆同樣大小的
  小圖示，使用者會找不到——測試通知按鈕曾經因為這樣「有做但找不到」
  （見 YT 頻道追蹤那節）。少用的動作（測試通知、匯出）收進帶文字
  標籤的「⋮」選單，常用動作才留在外面當獨立圖示。
- **大分類切換要用 `go`，不要用 `push`。** 側邊選單這種「換到另一個
  大類別」的導航，疊上去的話使用者在幾個大類別之間跳幾次，返回鍵
  要按老半天才回得去（2026-09-23 使用者實機回報）。只有真正「往下
  鑽」的子頁面（例如頻道列表點進頻道詳情）才適合用 `push`。
- **手機瀏覽器的邊界情況要用實機驗證，不能只信桌機測試結果。**
  桌機瀏覽器對很多限制（彈窗封鎖、使用者手勢判定）比手機寬鬆很多，
  同一個 bug 桌機測不出來、手機一用就中（見 YT 頻道追蹤「點影片打不
  開連結」那個坑，兩次修復桌機都測得過，真正修好是使用者拿手機截圖
  加主控台錯誤回報才抓到）。
- **新功能先出 HTML 設計稿讓使用者選，不要直接刻正式版。** 這份文件
  裡每個做出來的功能（日記、YT 頻道追蹤）都是先出好幾版
  `design-history/` 底下的 HTML 讓使用者挑方向，再照挑定的版本刻
  Flutter，不要自己直接決定要哪個設計就開工。
- **確認對話框跟提示訊息全 App 只用共用的那兩個函式。** 刪除、清空、
  離開不儲存這類「確定嗎？」用 `showAppConfirmDialog`
  （`lib/shared/widgets/app_confirm_dialog.dart`）；做完的提示用
  `showAppNotice`（頂端毛玻璃）。兩個都是文字居中、取消在左、紅色
  實心確認鍵在右。2026-10-02 使用者從
  `design-history/2026-10-02_確認對話框與提示五種風格.html` 挑了第 2 版
  ＋文字居中，並要求整個 App 統一——之前各頁自己組 `AlertDialog`，
  刪除鍵紅實心、紅字、藍字都有。不要在個別頁面再自己組確認框或
  SnackBar。（有輸入框、選單的編輯類對話框不算確認框，照舊各自組。）
- **長按操作選單全 App 只用泡泡橫列 `showBubbleMenu`**
  （`lib/shared/widgets/bubble_menu.dart`）：LINE／微信長按訊息那種，一條
  黑色泡泡浮在被按的卡片上方、尖角指向它，圖示在上短字在下，刪除放最右邊
  用分隔線隔開；上方放不下才改放下方。2026-10-02 使用者從
  `design-history/已選擇完成/2026-10-02_頻道長按選單五種風格.html` 挑了泡泡橫列並要求
  整個專案統一。不要再用 `showMenu` 或從底部滑出的操作面板當長按選單。

## 一、單字的三種狀態

狀態不是存下來的欄位，是**每次即時算出來的**，判定只在
`lib/domain/models/word.dart` 的 `statusWith()` 一個地方。
其他任何檔案都不准自己寫判斷條件。

| 狀態 | 條件 | 標籤色 |
| --- | --- | --- |
| 掌握 | 見下面兩條進法 | 綠 |
| 待複習 | 考過但還沒到掌握。含答錯過的，也含答對過但還沒到門檻的 | 棕 |
| 新字 | 從來沒被考過 | 灰 |

### 為什麼只有三種狀態

使用者 2026-09-11 拍板：「未確認？那就是待複習啊，已掌握就是已掌握的」。

曾經多開一個「未確認」放答對過但還沒到門檻的字，但對使用者來說
那跟錯過的字是同一件事：都還沒到掌握，都該回來。分兩類只是多一層概念。


### 為什麼待複習用棕色不用紅色

紅色是「剛剛答錯」那一刻的顏色。待複習是一個狀態不是一個錯誤，
天天看到一整排紅色會焦慮。沒考過用灰色，因為它不是問題，
只是還沒碰過，不該跟待複習搶注意力。

## 二、怎樣才算掌握

兩條路，走哪一條看它有沒有錯過。

**從沒錯過的字**：答對達到 `confirmRight` 次（預設 4，使用者 2026-09-16 從 3 調高）。

**錯過的字**：答對次數要達到答錯次數的 `recoveryRatio` 倍
（預設 5，使用者 2026-09-16 從 7 調低）。

```
錯 1 次 → 要答對 7 次
錯 5 次 → 要答對 35 次，整個字總共被考 40 次
```

倍率訂得重是刻意的。錯過的字要能相信它真的會了，就得多考幾次。
兩個數字都能在設定裡改。

**掌握之後對錯次數繼續累加**，不會歸零也不會停止計數。
`rightNeededFor()` 回傳 0 只代表「不差了」，不是把資料清掉。

門檻調高之後，原本掌握但沒到新門檻的字會自動掉回去。
這是刻意的：門檻變嚴就該重新驗證。

## 三、一輪出什麼題

一輪十題，組成是：

| 來源 | 題數 | 參數 |
| --- | --- | --- |
| 待複習 | 7 | `pendingPerRound` |
| 句型 | 1 | `sentencePerRound`，從新字的配額挪過來 |
| 新字 | 1 | 剩下的位置 |
| 已掌握 | 1 | `masteredPerRound` |

句型（見十、單字類別的「句型」小節）是使用者 2026-09-16 決定加的，
配額**從新字挪一題過去，不是額外加題數**：`freshPerRound` 的算法變成
`roundSize - pendingPerRound - masteredPerRound - sentencePerRound`。

### 補位規則

哪一種不夠就用別的補，一輪的題數固定不變：

```
缺的時候往下補，順序是「最需要練的先補」：
待複習 → 新字 → 已掌握
```

句型不用進這條補位鏈：句型抽不到（例如句型庫被抽完）時，
`freshPerRound` 的算法本來就已經把句型的缺額算進去了，
那個名額會自動變成多一題新字，不需要另外處理——這個名額本來就是
從新字挪過去的，退回去很自然。

只有單字庫本身比一輪還小的時候才會缺題，那時候不會重複出同一個字。

### 排序

- 待複習：先算 `rightNeededFor()`（離掌握還差幾次答對，見二、怎樣才算掌握），
  排出「離掌握最遠」到「最近」的順序，同樣差距的排最久沒考的在前面——
  但這個排序**只用來決定誰擠得進候選池前 `pendingCandidatePoolSize` 名**
  （預設 30，設定頁可調），不是最終出題順序。
  真正出題分兩段：
  1. **先保留一個名額給「最接近掌握」的字**（使用者 2026-09-15 決定）：
     待複習池裡 `rightNeededFor()` 最小的那個，就算它排不進候選池
     （它是離掌握最近，不是最遠，本來就不會落在候選池裡）也直接抓。
     理由是不該每輪都在啃最遠的字，快完成的字也該有機會被送過門檻。
  2. **剩下的名額從候選池裡完全隨機抽**：進了候選池之後排名就不算數了，
     差距大小、多久沒考都不影響被抽到的機率，是均等的隨機抽樣。
     原本死死拿排最前面的幾個，同一批最需要練的字每輪都長一樣，
     練久了會膩；改成候選池隨機抽，一樣優先練最需要的那一批，
     但候選池裡誰出現會换著出。
  每一輪都是重新載入最新的對錯次數再重新排候選池，
  不是算過一次就快取住重複用（答完題會讓單字庫的快取失效，
  見七、資料放哪）。
  題數不夠時的補額不用隨機，照候選池的優先順序直接補，
  這裡要的是把題數補滿，不是換花樣。
- 墊底的已掌握字：最久沒考的優先，**不看對錯次數**。這批字反正都已經
  達到掌握門檻，考較久沒碰的比考剛答對沒多久的更有意義。
- 新字：洗牌。題庫是照字母排的，不洗牌會整輪都是同一個字母。
- 句型：有自己獨立的一套待複習/新字/已掌握三個池子，排序規則跟一般單字
  完全一樣（`_sentencePendingPool`／`_sentenceFreshPool`／
  `_sentenceConfirmedPool` 直接重用同一套排序邏輯），只是資料來源只看
  標了 `sentenceTag`（「句型」）這個標籤的 `Word`。選一句的優先序也是
  「待複習 → 新字 → 已掌握」，跟主要三池同一套精神，只是句型只有一句
  名額，不用候選池隨機抽那一段——句子數量還很少，隨機抽的意義不大，
  直接照優先序拿。

三個池子都用 `statusWith()` 判斷，不在出題規則裡自己寫條件，
不然狀態定義改了這裡會默默跟不上。句型的三個池子也是同一套 `statusWith()`，
只是多了「是不是句型」這個篩選條件（`Word.tags.contains(sentenceTag)`），
一般單字的三個池子反過來也要排除句型，不然句子會混進單字池被抽走。

## 四、題型

三種，在設定裡切。預設只點選，打字題要自己開。

| 模式 | 內容 |
| --- | --- |
| 只點選 | 全部英翻中，按會或不會 |
| 混合 | 多數點選，少數幾題中翻英要打字，題數可調 |
| 只打字 | 每題都要打出來 |

出題規則只看 `effectiveTypeQuestions`，不自己判斷模式。

### 已掌握的回考題例外：一律中翻英打字

不管上面選哪個模式，一輪裡回考的那個已掌握的字（`masteredPerRound`）
固定用中翻英打字，不會是點選題。使用者 2026-09-15 要求的：
掌握只代表看得懂，不代表拼得出來，用點選題回考測不出這件事，
拼錯了也留不下打錯在哪裡。

這題算進 `effectiveTypeQuestions` 的總額裡，不會讓一輪的打字題數超過設定值。
`QuestionPicker.pick()` 的 `forceMasteredType` 參數控制這個行為，
（原本偽裝模式會關掉它；偽裝模式 2026-10-05 使用者要求拔掉了，App 裡
現在一律開著。）

拼錯的內容照打字題原本的規則存進紀錄（見「六、紀錄」），
不用另外處理，本來就會留下實際打了什麼。

**會與不會兩顆都隨時能按**，不用先翻卡片。翻不翻由使用者決定。
打字題也有「不會」，按了直接判錯並揭開答案，不逼人硬湊一個錯的上去。

### 滑卡

按鈕之外也能滑：**右滑會、左滑不會**，拖到一半卡片會染上綠或紅。
按鈕照樣留著，滑卡是多一種答法不是取代。

打字題不能右滑說自己會，一定要打出來才算。還沒判定時左滑等於按不會，
判完之後左右滑都是下一題。

### 打字題怎麼作答

- **沒有提示字母**（使用者 2026-09-15 決定）。以前會先露出第一個字母，
  但看中文就該自己拼出來，露一個字母等於送一半分。
- 字直接打在底線空格上，答案幾個字母就幾格，長的字會自動縮小排進一行。
- **打滿格數就自動判定**，不用按送出。送出鍵留給想提早交的人。
- 打錯時卡片閃一下紅、左右抖一下，手機會震一下。按「不會」不閃，那不是打錯。
- **答對 1 秒後自動跳下一題**（使用者 2026-09-15 決定），不用再按「下一題」，
  連對很多題時手不用一直點。答錯還是留著「下一題」按鈕，
  答案要留給使用者自己看完再往下走，不能也自動跳。

### 拼字判定

`lib/domain/spell_judge.dart`。幾條規則是使用者決定的，不要因為
「好像太嚴」就自己放寬，也不要因為「好像太鬆」就自己收緊：

1. **不管大小寫**
2. **複數算錯**
3. **a 和 an 視為不同的字**
4. **標點符號不算數**（使用者 2026-09-16 決定，句型上線後才加的規則）。
   考的是「打不打得出這句話」，不是標點符號背得多熟，
   `You're` 打成 `Youre`、句尾漏打句號都不算錯。

做的事：去掉前後空白、把大小寫拉平、拿掉標點符號只留英數字和空白、
多個空白收成一個。不做字根還原也不做複數還原。

**大小寫沒有例外**，曾經考慮過「月份這種專有名詞開頭一定要大寫」，
討論後決定不加：句子開頭本來就會大寫，程式沒辦法只憑存的字串分辨
那個大寫是「文法規定」還是「剛好在句首」，勉強做只會多一個要人工
標記的欄位，為了這種次要重點不值得，也跟「不管大小寫」的既有原則衝突。

畫面的空格列、輸入框的字數上限都要用 `SpellJudge.stripPunctuation()`
算過的長度，不能用原始的 `word.word.length`——不然句型的標點符號會
占掉空格列的格子，跟拿掉標點符號後的答案對不齊，也會導致打字的人
永遠湊不滿格數、自動判定不會觸發。打字題的輸入框也直接用
`FilteringTextInputFormatter` 擋掉標點符號，乾脆不讓打，兩邊才會對齊。

## 五、每日上限

預設一天 5 輪，做滿就**真的按不下去**，不是只跳提示。
這是防止做過頭然後整個放棄的核心。

**時間不當限制條件**（使用者 2026-09-15 決定）。以前是輪數或
`minutesPerDay`（預設 15 分鐘）哪個先到算哪個，改成只看輪數：
想久一點才答不該被時間趕著擋住。`practiceSeconds` 還是照樣記，
首頁環底下、總紀錄頁都還看得到花了多久，只是不會因為秒數多了
就按不下去。`DailyLimit.reached()` 只看 `roundsDone`，不要自己加回時間判斷。

（原本偽裝模式不受這條管；偽裝模式 2026-10-05 使用者要求拔掉了，
現在每一輪都算進今日用量。）

跨日自動歸零，只看年月日不看時分秒。

## 六、紀錄

### 只增不改

`lib/data/repositories/history_repository.dart`。這是整套資料的權威。

**單字上的對錯次數不是自己累加的，是從紀錄加總算出來的。**
這樣兩邊（對話與 App）各自出題各自追加，合併時去重就不會有人的紀錄被吃掉。

### 每答一題就寫一次

不是整輪結束才寫。中途關掉瀏覽器或被系統收掉都不會掉資料，
半輪也留得下來。整輪做完才補上真正的耗時，並計入今日用量。

### 合併去重看內容不看編號

指紋是「輪次＋單字＋時間＋對錯」。兩邊剛好用到同一個輪次編號
也不會互相蓋掉，因為內容不同就是不同的兩筆。

### 每一題記什麼

輪次、單字、對錯、作答時刻、想了幾秒、題型、打字題實際打了什麼、
是不是回考。

打字題留下輸入內容是刻意的：光知道答錯沒有用，
要看得出當初拼錯在哪個字母才學得到東西。

## 七、資料放哪

```
En 資料夾的檔案 ──手動複製進 assets──> App 自己的儲存
```

單向。App 的成績存在裝置裡，不會回寫檔案。

- 原生：App 私有目錄
- 網頁：瀏覽器 IndexedDB，清掉就沒了

### 設定也要多裝置同步（2026-10-12 使用者要求）

新增的設定（開關、選項、數值）一律接進雲端同步，不要做成只存本機：
一個功能的設定整組存成一筆「值＋改的時間」，同步時比時間，後改的贏
（範本：`UsdtTwdRateStore`／`YtDisplayPrefsStore` 跟
`R2SyncService.syncUsdtTwdRate`／`syncYtDisplayPrefs`），同步帶回新的
要順便更新畫面用的 provider。新欄位在 `fromJson` 裡給預設值，舊裝置
上傳的檔案才讀得進來。

只有一個值的設定用 `StampedSettingStore`＋`R2SyncService.syncStampedSetting`
（舊版直接存值的也讀得進來）。2026-10-15 補上以前只存本機的：點影片時、
播放器樣式、訂閱人數更新頻率、日文進度圈、首頁樣式，還有頻道頁的最近搜尋。

例外：裝置本身的東西（API 金鑰、R2 金鑰這類帳密）不同步。

### 匯出紀錄

不同裝置（手機、電腦）各自的作答紀錄存在各自的裝置裡，**不會自動合併**。
使用者 2026-09-15 要求的：總紀錄頁右上角有一顆匯出按鈕
（`HistoryRepository.exportText()`），把紀錄轉成跟 `history.txt` 同一種格式的
文字，跳對話框讓使用者自己貼給人工整理、合併回題庫的紀錄檔。

**主要動作是下載成檔案**，不是只能複製（使用者 2026-09-15 補的要求）：
網頁版跟手機瀏覽器打開同一個網頁版都是走瀏覽器原生下載
（`data/export/file_download.dart`，用 `dart:html` 的 Blob + `<a download>`），
不用另外裝原生 App 或外掛。對話框裡也會先顯示檔名跟預估檔案大小
（`B`／`KB`／`MB`，看 `_formatSize()`），下載前就知道多大。
複製到剪貼簿留著當備用，萬一某些瀏覽器環境擋下載還有得用。

原生（Android/iOS）平台目前呼叫下載會直接回傳失敗，跳提示改用複製，
因為這個 App 實際上只有網頁版在用，原生版還沒做存檔到裝置的功能，
用條件匯入（`if (dart.library.html)`）分平台實作，不是判斷 `kIsWeb` 再
if/else——`dart:html` 在非網頁平台編譯不過，一定要用條件匯入才能兩邊都編譯。

這條路是單向的另一半，只是方向反過來（裝置 → 人）：App 本身還是不會
自動把匯出的內容寫回任何檔案，也不會自動跟另一台裝置同步，
合併這件事目前完全靠使用者手動下載、傳出去給人整理。

打包資料帶版本號 `SeedSource.bundleVersion`。
**每次從 En 資料夾重新複製檔案進 assets 就要加一**，否則 App 不會去讀新內容。
忘了加會以為程式壞了。

同步時只更新靜態欄位（中文、詞性、階段、例句、標籤），**不碰對錯次數**，
那是算出來的。App 裡有、打包資料沒有的字一律保留。

標籤（`Word.tags`）同步時是**合併不是覆蓋**：題庫跟 `words.txt` 都有標籤時，
兩邊取聯集，不然題庫標的分類考過一次就會被 `words.txt` 蓋掉。

**`words.txt` 也能標詞義豐富度（`senseCount`）**（使用者 2026-09-16 發現的洞：
以前只有 `seed-words.txt` 能標，考過但題庫沒收的字完全沒地方標，兩邊本來
就該一致，已經補上）。欄位接在 `tags` 後面，順序是 `... / tags / sense`。
合併規則：`senseCount` 只有一個值，沒辦法取聯集：**題庫標過就以題庫為準**，
題庫沒標才讓 `words.txt` 補上，不會互相覆蓋。所以 `words.txt` 目前欄位是
`no/word/pos/zh/example/added/right/wrong/last_test/tags/sense`，共 11 欄。

`senseCount` 的資料本身：2026-09-16 使用者要求把 `words.txt` 裡的字全部
逐字用字典判斷義項數標一次，標準跟 `seed-words.txt` 那次一樣：1 個義項＝
單義，2-4 個＝多義，5 個以上＝極多義。同一天又跟 En 資料夾合併了一批新字
（788 → 1008 個），合併當下用的是舊版 `words.txt`，把剛標好的分類整個蓋掉
變回空的，事後發現又重新套了一次，這次連新併入的 220 個字也一起判斷完，
現在 1008 個字全部都有 `senseCount`。

**這個檔案曾經短暫多出一個 `topics` 欄位，後來又拿掉了**——同一天有另一個
平行 session 誤以為 `words.txt` 也跟 `seed-words.txt` 一樣有獨立的 `topics`
欄位，把 `word_seed_loader.dart` 改成第 11 欄當 topics、第 12 欄當 sense
讀，導致 sense 永遠讀空。這個教訓現在已經不會再發生：**類別這個概念本身
被拿掉了**（見「十、單字類別」），全部併進 `tags`，不會再有哪個檔案該不該
開 `topics` 欄的問題。改欄位相關的程式前還是要養成習慣：**先看資料檔實際
欄位數，不要憑印象假設兩個檔案格式一樣**，這次的坑就是這樣踩到的。

### 單字題庫還有一個固定搭配的兄弟檔

`assets/data/seed-phrases.txt` 放高頻固定搭配（像 apply for a position、
meet the deadline），**欄位規則跟 `seed-words.txt` 完全一樣**，用同一個剖析器讀，
讀完直接併進同一個單字池，出題、篩選、單字庫清單都跟一般單字一視同仁，
不是另外開一個獨立系統。id 編號接續 `seed-words.txt` 往下排，不要重疊
（使用者 2026-09-15 決定）。

要加新的固定搭配就直接照 `seed-words.txt` 的格式加一行進 `seed-phrases.txt`，
不用動程式。

### 加句子用腳本，不要手動改檔案

`scripts/add_sentences.ps1` + `scripts/staging_sentences.txt`
（使用者 2026-09-16 決定）：要加新句子先寫進 `staging_sentences.txt`
（欄位用「|」分隔，檔案開頭有完整說明），跑 `add_sentences.ps1`。
腳本會用整句英文（小寫、去頭尾空白）比對 `sentences.txt` 裡有沒有重複：

- 句子已存在：只合併 `tags`／`relatedWords`（取聯集），不動 `pos`／`zh`／
  `grade`／`sense`；如果 staging 填的中文跟現有的不一樣，只是印警告
  提醒可能打錯字，不會覆蓋。
- 句子不存在：新增一行，編號自動接續 `sentences.txt` 目前的最大編號。
  每一句都保證會有 `sentenceTag`（「句型」）這個標籤，就算 staging 沒填
  腳本也會自動補上——這個標籤是出題規則拿來判斷「這是句子不是單字」的
  依據，漏了會讓句子安靜地從句型池消失。

跑完會自動把 `# seed-version` 加一（只有真的新增句子才加，只合併標籤
不算）、清空 staging 檔、重新對齊整份檔案的欄寬。**`bundleVersion`
不會自動改**，那是 Dart 原始碼，腳本結尾會印提醒，交給人手動確認比較安全。

**這是 App（lume）專案自己的腳本，管的是這個專案的 `sentences.txt`**。
En 資料夾那邊有一支邏輯相同但完全獨立的 `add_words.ps1`
+ `staging_words.txt`，管的是 En 那邊自己的 `words.txt`——兩支腳本、
兩個專案各管各的資料，故意不合併成一支共用腳本，因為兩邊資料的生命
週期不一樣（見下一節「跟 En 資料夾的分工」）。

### 跟 En 資料夾的分工

`assets/data/words.txt`（已經考過的字）跟 `assets/data/history.txt`
（測驗紀錄）**這兩個檔案的權威版本在 En 資料夾那邊，不在這裡**。En 側
2026-09-16 做了一支常駐腳本 `merge_data.ps1`：把這邊（App）匯出的
`history.txt` 整批併進 En 那邊的 history（不去重）、用合併後的完整
history 重新加總每個字的 `right`／`wrong`／`last_test`、寫回兩邊的
`words.txt`、清空這邊的 `history.txt`。**這支腳本假設 En 那邊的
`words.txt` 一直是這邊（App）的超集**，合併時是拿 En 的版本當基準。

**這代表：不要在這裡（lume）獨立修改 `assets/data/words.txt` 或
`assets/data/history.txt` 的內容，除非先跟 En 那邊講好**——這裡改了但
沒同步過去，下次 En 跑 `merge_data.ps1` 就會被蓋掉，白做工。2026-09-16
就踩過這個坑：這裡幫 `words.txt` 全部 1008／1015 個字逐一標好了
`senseCount`，因為只改了這邊、沒有同步進 En 的版本，En 跑完
`merge_data.ps1` 之後這批分類又整個消失了（第二次遇到同一種問題，
第一次是 En 那邊手動合併時用了舊版覆蓋，這次是常駐腳本假設方向反過來
把這邊的新資料蓋掉）。以後這兩個檔案要嘛完全不要在這裡手動改，要嘛
改完要另外通知 En 那邊同步過去，不能只改這邊就當作完成。

這次的處理方式（使用者 2026-09-16 決定）：先在這裡重標一次
（1015 個字全部逐字補回 `senseCount`：626 單義、327 多義、62 極多義），
再請使用者拿這批結果去 En 那邊「照抄」進它的 `words.txt`，不是等 En
先同步。往後如果又遇到這兩個檔案的分類被合併蓋掉，同樣的作法：這裡先
重標，交給使用者去同步，不要自己猜測 En 那邊什麼時候會同步而按兵不動。

- **結果頁一定要把答錯和沒答出來的字全部列出來並附中文**，一個都不能漏，
  也不要附記憶點。使用者要的是答案清單，不是講解。
- **結果頁的「這輪」要能分出新字、待複習、已掌握三種來源**
  （使用者 2026-09-15 決定）。`QuizQuestion.isMasteredReview` 專門標記
  已掌握的回考題，跟泛用的 `isReview`（待複習和已掌握都算）分開，
  不然 `masteredPerRound` 那一題答完會看起來憑空消失，使用者會以為沒抽到。
  已掌握這一列題數是 0 就不顯示（那一輪的名額被讓給待複習了，見三、
  一輪出什麼題的補位規則），不要秀一個永遠 0/0 的空列。
- **偽裝模式已拔掉**（2026-10-05 使用者要求）。舊紀錄裡的 `stealth` 欄位
  留著只為了讀得懂以前存的資料，畫面上不再顯示。
- **單字分級只有四級**：國小、國中、高中、大學。曾經細分到小一小六，
  但那層沒有官方依據，猜出來的年級只會讓人誤以為很準。
- **首頁圓環底下每天一句話**，五十句輪完才重來，用日期算不存狀態。
  語氣刻意不熱血，要讓人覺得今天這樣就夠了，不是再多做一點。

## 九、參數一覽

全部在 `lib/domain/rules_config.dart`，設定頁改的是覆寫值。

**全新使用者（還沒存過設定）的預設值來自 `assets/config/app_defaults.yaml`，
不是直接讀這個 class 的建構子預設**（使用者 2026-09-17 決定）。原因：這組
數字是「遊戲平衡」性質，會一直微調，改設定檔部署就好，不用重新編譯。
格式選 YAML 不選 JSON，是因為 JSON 不能寫註解——這種每個數字都要
解釋才看得懂用途的設定檔，沒有註解等於沒人敢改，所以 `app_defaults.yaml`
裡每個欄位都比照 `rules_config.dart` 的 doc comment 寫了完整說明。

`app_defaults.yaml` 是 App 裡所有「調數字不用重新編譯」設定的集中地，
不是只有學習規則——發音語言/音調（`ttsLanguage`／`ttsPitch`）、啟動畫面
停留時間（`splashHoldMs`）也在裡面，見 `lib/data/seed/app_defaults_loader.dart`。
**這兩塊跟學習規則的容錯策略不一樣**：學習規則沿用既有的
`RulesConfig.fromJson`，讀不到／壞掉／漏欄位會 fallback 回
`rules_config.dart` 建構子裡寫死的保險值；發音跟啟動畫面**沒有**
code 端備份值，是唯一來源，讀取失敗就直接丟例外讓 App 炸出來
（使用者 2026-09-17 明確說不用留備份，理由跟這個 App 一貫「出錯就
出錯」的態度一致——沒必要為了兩個不影響核心排題邏輯的次要設定，
維護一份很少會被用到的容錯路徑）。之所以學習規則還留著保險，單純
是因為 `RulesConfig.fromJson` 這個容錯本來就存在（是給使用者存在
本機的舊設定做欄位補齊用），順便沿用不算額外成本，不是「學習規則
比較重要所以特別留一手」。

讀取邏輯在 `lib/data/seed/app_defaults_loader.dart`
（`loadDefaultRulesConfig()`／`loadTtsDefaults()`／`loadSplashHoldDuration()`，
都是用 `package:yaml` 解析）。`test/data/seed/app_defaults_loader_test.dart`
會真的把這個檔案讀進來斷言幾個數值，防止設定檔路徑或格式壞掉時
悄悄掉進 fallback（學習規則那塊）或應該要炸卻沒有炸（發音／啟動畫面
那塊）、沒人發現。

因為發音設定改成非同步讀取，`ttsServiceProvider` 從 `Provider` 改成
`FutureProvider`，讀取端要用 `ref.read(ttsServiceProvider.future)`
（`SpeakerButton` 已經改好）；`SplashPage` 也一樣，先讀完
`splashHoldMs` 才開始計時再跳轉首頁。

下面這張表的「預設」欄位，就是 `app_defaults.yaml` 學習規則那節目前
的值（跟 Dart 那份保險預設同步著，改了其中一邊記得另一邊也要改）。

## 十、單字類別跟標籤

**2026-09-16 使用者決定拿掉「類別」這個獨立分類軸，全部併進標籤
（`Word.tags`）**。在此之前類別（topic）跟標籤（tags）是兩個平行系統：
類別是題庫檔專屬一欄、固定選項的 `WordTopic` enum（食物、居家、月份、
數字、顏色、水果、句型），只能靠改程式加新值；標籤是自由文字，想標
什麼就標什麼（像多益、工程師），但只能拿來搜尋，沒有下拉篩選、卡片上
也不會顯示。使用者發現這兩套東西其實是同一件事——都是「一個字可以貼
好幾個」的自由分類——沒必要分成兩條路、還要各自維護一套 UI，於是決定
拿掉類別，單字庫的「類別」下拉改成直接對 `tags` 出現過的所有值，不是
列舉某個 enum。以前六個類別的中文字串（食物、居家、月份、數字、顏色、
水果）現在都變成普通標籤，資料沒有損失，只是換了個位置存。

**這是不留相容路徑的斷版改動**：`Word.fromJson` 沒有幫舊版本地存檔
（還存著獨立 `topics`／`topic` 欄位的那種）做搬遷，讀到舊格式就是讀不到
分類，不會報錯也不會補救（使用者 2026-09-16 明確決定：「不用，出錯就
出錯，要整個改版」）。理由是這個專案目前只有使用者自己在用，資料都在
題庫檔（`seed-words.txt` 等）裡，本地存檔本來就會被 `bundleVersion`
同步覆蓋掉靜態欄位，沒有真的需要救的舊資料，加相容碼只是徒增一段
以後沒人記得為什麼存在的程式。

**加新分類完全不用改程式**：以前要加類別得先去 `WordTopic` enum 加一個
值，現在題庫檔那一欄直接打字就好，下拉選單會自動列出資料裡實際出現過
的所有標籤，這是這次改動最主要的好處。

一個字可以同時貼好幾個標籤，`Word.tags` 是清單，題庫檔那一欄多個標籤
用「、」分隔，例如 `食物、水果、顏色`。篩選看的是「有沒有包含」這個
標籤，不是「剛好只有這一個」；下拉選單的數字統計也是每個標籤各自加總，
一個字算進好幾個標籤是預期的，全部標籤加起來會超過單字總數。

以下是幾個標籤各自的由來，內容還是舊的，只是現在存放的位置從「類別」
變成「標籤」：

- **居家**是泛指，包含房間名稱、建築部位、家具日用品、餐具。餐具沒有
  另外拆出去：要複習廚房的時候，碗跟廚房本來就會一起想到，拆開反而
  要切兩次篩選。
- **月份**是使用者 2026-09-15 加的：1 到 12 月的英文單字（`January`～
  `December`，`May` 併進 `may` 那一列，因為它跟助動詞 may/might 是
  同一個拼字）全部標成月份，方便單獨複習這一小群字。
- **數字**也是使用者 2026-09-15 加的：基數（one～ninety）、序數
  （first、second、third）、量詞（dozen、hundred、thousand、million）、
  zero，全部標成數字。
- **顏色**也是使用者 2026-09-15 加的：black、blue、brown、gold、gray、
  green、pink、purple、red、white、yellow 這些原本就有的顏色字，加上
  新補的 silver、navy、beige、maroon、turquoise，全部標成顏色。
  `orange` 額外同時標食物、水果、顏色三個。
- **水果**也是使用者 2026-09-15 加的：從食物類別裡挑出真正的水果
  （apple、banana、grape、guava、lemon、orange、papaya、peach、pear、
  strawberry、watermelon），連同新補的 mango、pineapple、kiwi、cherry、
  coconut，全部**在原有食物分類上再加水果**，不是取代，兩個標籤並存。

**句型是唯一的例外**：其他標籤單純是瀏覽/篩選用的，句型不是——標了
`sentenceTag`（字串常數，值是「句型」）的字會被出題規則獨立看待
（見三、一輪出什麼題），細節見這節最後的「句型」小節。之所以句型這個
標籤值得留一個程式常數（`sentenceTag`），而不是像其他標籤一樣散在資料
檔裡就好，是因為它是唯一一個真正影響出題邏輯的標籤，其餘標籤都只是
給畫面篩選用，程式完全不關心標籤的實際內容。

顯示位置：

- 單字庫每一列的中文後面一個細框小標籤（`TagBadge`）。
- 單字詳情頁標題底下，跟詞性中文同一行。
- 沒有任何標籤的不顯示，免得整排都是空的很吵。

樣式刻意做得比狀態標籤輕，只有細框沒有底色。
標籤是附加資訊，不該跟「掌握 / 待複習」搶注意力。

### 篩選放在哪

篩選列的左邊是狀態（可橫向滑），右邊固定一個標籤下拉。

沒有塞進搜尋框，理由是搜尋框留給打字，兩件事混在一起會變得又擠又難按。
下拉固定在右邊不跟著滑走，狀態再多也不會把它推出畫面。

下拉選單列的是資料裡實際出現過的所有標籤值（`LibraryData.tagCounts`
的鍵，字母排序），外加一個「未分類」代表完全沒有任何標籤的字
（`untaggedLabel` 這個字串常數，跟真正的標籤字串共用同一個 Map 存）。

**字母序之上還可以疊使用者指定的排序偏好**（使用者 2026-09-17 決定，
設定放 `assets/config/app_defaults.yaml` 的 `libraryTagAdjacentGroups`／
`libraryTagTrailingOrder`，讀取邏輯在 `app_defaults_loader.dart` 的
`loadLibraryTagOrder()`，實際排序邏輯是 `library_page.dart` 的
`sortLibraryTags()`，有測試在
`test/features/library/sort_library_tags_test.dart`）：

- `libraryTagAdjacentGroups`：列出來的標籤要在選單裡相鄰出現，順序
  照列的順序。目前設的是 `[git, 工程師]`——git 是 ASCII，字母序本來
  就會排在所有中文標籤前面，這是預期行為，不是 bug，使用者只要求
  「相鄰、git 在前」，沒要求特定絕對位置。
- `libraryTagTrailingOrder`：列出來的標籤要照這個順序排在一般標籤
  清單最後（「多標籤（2 個以上）」那個特殊選項是結構上固定在整個
  選單最底部，不受這裡影響，見下面 [multiTagLabel] 的說明）。目前
  設的是 `[中等字, 基礎字, 超基礎字]`。
- 兩種規則都是「有這個標籤就這樣排，沒有就跳過」，不會因為資料裡
  缺一個標籤就整個排序邏輯出錯——這個設定讀失敗（檔案壞掉、格式
  錯）也直接退回純字母序，不會讓 App 打不開，跟學習規則／發音／
  啟動畫面那三節「讀不到就丟例外」的態度不一樣：排序偏好本身不影響
  資料對不對，不值得為這個讓 App 炸掉。

**狀態和標籤是「且」的關係**，兩個可以同時生效，
例如「待複習」加「食物」就是只看還沒學會的食物字。

### 同一種狀態裡怎麼排

狀態分組（待複習／新字／已掌握）永遠在最外層，這裡講的是分組**裡面**
的順序，不會把不同狀態的字混在一起排。

預設是**練習次數（答對＋答錯）多到少**（使用者 2026-09-15 決定），
不是題庫原本的編號。理由是練習次數多代表這個字被回考很多次，
比單純的題庫編號更值得先看到。

搜尋框右邊有一個排序按鈕（`Icons.sort_rounded`）可以切換，還有三個選項：

- **題庫編號**：改預設之前的排法，留給想找回舊排序的人。
- **權重高到低**（使用者 2026-09-15 決定）：用 `Word.masteryWeight()` 排，
  **權重高的排最前面**——不是把最差的排前面，是把掌握得最紮實的排前面。
  跟出題規則裡待複習池排序用的是同一套邏輯（見二、怎樣才算掌握），
  錯過的字要答對次數達到答錯次數的 `recoveryRatio` 倍才算打平，
  不是單純比錯的次數多少，這樣不同路線的字才排得進同一把尺。
- **單字長度（短到長）**：照英文單字的字母數排，短的在前面。

`LibrarySort` 這個 enum 目前四個值，要加新的排序方式就在那裡加一個值，
畫面的選單會自動長出新選項。

### 詞義豐富度

題庫有一欄是詞義豐富度，跟標籤是**完全獨立的兩個分類軸**，
不要混在一起判斷或顯示。分三級：單義、多義、極多義，其餘未分類
（使用者 2026-09-15 決定）。

判斷標準是查字典的義項數，這是人工標記時要靠的標準，
App 本身不會自動算意思數量：

| 級別 | 義項數 |
| --- | --- |
| 單義 | 1 個 |
| 多義 | 2 到 4 個 |
| 極多義 | 5 個以上 |

要標記就是兩步，畫面不用改：

1. `WordSenseCount` 已經有 `none`／`single`／`few`／`many` 四個值，不用加新的。
2. 題庫檔那一欄填上對應的中文（單義／多義／極多義）。

顯示位置、樣式、篩選規則都跟標籤一模一樣：單字庫每一列跟詳情頁各有一個
細框小標籤，未分類不顯示；篩選列的標籤下拉右邊再加一個詞義下拉，
跟狀態、標籤三個是「且」的關係，可以同時生效。

### 句型

使用者 2026-09-16 決定加的：句型是整句英文直接背，不是拆單字學，
但**跟單字共用同一套資料結構跟作答邏輯**（使用者明確要求「跟單字依樣」），
不是另外開一個 `Sentence` model——這樣句子也會有自己的答對/答錯次數、
也會走 `statusWith()` 的掌握判定，跟單字待遇一致，也不用維護兩套
幾乎一樣的邏輯。

資料放在 `assets/data/sentences.txt`，欄位規則、剖析器都跟
`seed-words.txt`／`seed-phrases.txt` 一樣（見七、資料放哪），差別是：

- `word` 欄放整句英文（例如 `I don't care.`），不是單字。
- `pos` 欄固定填 `sent.`，只是佔位，不是真的詞性。
- `tags` 欄一定要有 `sentenceTag`（「句型」），出題規則靠這個把句子跟
  一般單字分開，可以跟其他自由標籤用「、」並列，例如 `句型、多益`。
- `sense`（詞義豐富度）對整句沒意義，填 `-`。
- 最後一欄是新加的 `Word.relatedWords`：這句用到哪些學過的單字，
  用「、」分隔多個，例如 `feel、sick`。**存的是文字不是 id**——文字
  好讀好編輯，代價是拼錯就對不上，這是使用者 2026-09-16 權衡過的決定。
  跟 `tags`（自由分類，像多益、工程師、句型）是不同欄位、不同語意，
  不要混用：`tags` 是分類，`relatedWords` 是「這句用到哪些字」的
  交叉參照。

出題規則見三、一輪出什麼題跟裡面的「排序」小節：句型有自己獨立的
待複習/新字/已掌握三個池子，一般單字的三個池子要排除句型，
兩邊互不干擾。

## 十一、筆記分三本

首頁的燈泡圖示進「筆記」，上面用標籤切換三本：

| 本 | 放什麼 | 檔案 |
| --- | --- | --- |
| 用法地雷 | 講了會出事的字，像 fat、napkin | `usage-notes.md` |
| 近義字 | 選哪個比較準的字，像 quiz / test / exam | `word-choices.md` |
| 義項解析 | 多義、極多義的字，常見意思一次看完，像 back、hot、run | `sense-notes.md` |

三本格式完全一樣，共用同一套剖析與排版。
要加第四本就在 `NoteCollection` 加一個值，再放一個同格式的 md 進 assets，畫面不用改。

義項解析是使用者 2026-09-15 決定加的（見下面「義項解析標記」），
一則一個字，用表格把常見的意思由多到少列出來，不是一則對到多個字，
所以每則的「相關單字」永遠只有一個字。**一次補幾個字就好**，
不用逼自己一次把所有多義、極多義的字都補完。

### 地雷字標記

有些字講錯會失禮或被誤會，例如 napkin 在美式英文裡有時候指衛生棉，
fat 直接對人講很不禮貌。這種字在單字庫和單字詳情會多一個黃色的「地雷字」標記。

**哪些字算地雷不是另外維護的名單**，是從 `用法地雷.md` 每則結尾的
「相關單字」那一行推出來的。寫了筆記那幾個字就自動被標上，不會忘記同步。

單字詳情上的標記可以點，直接跳到對應的那一則。
清單上的不給點，免得跟整列的點擊打架。

要新增地雷字就是寫一則筆記，記得在結尾加上相關單字。

### 義項解析標記

多義、極多義的字（見十、單字類別的詞義豐富度）如果有對應的義項解析筆記，
單字詳情頁的詞義標籤會多顯示「· 看義項」，點下去跳到那一則。
跟地雷字標記同一套做法：**哪些字有義項解析不是另外維護的名單**，
是從 `義項解析.md` 每則結尾的「相關單字」推出來的。

沒寫筆記的多義字，詞義標籤還是會顯示（單義／多義／極多義），
只是不能點，因為沒有東西可以跳。單字庫清單、已經掌握頁那邊的詞義標籤
一律不給點，只有單字詳情頁才給點，跟地雷字標記的規則一樣。

## 十二、已經掌握那一頁

入口在單字庫標題列右邊的獎章圖示。

跟單字庫的「掌握」篩選不一樣：那裡是一列一行的清單，
這一頁一個字一張卡，**例句直接攤開**，重點是看得到怎麼用，不是數數量。

每張卡有：單字、詞性中文、例句、答對答錯次數、地雷字標記、標籤、詞義豐富度標記。
點卡片會進單字詳情看完整作答歷史。

排序是最近考過的排前面，剛掌握的那個會在最上面。

頁尾有一句提醒：掌握之後對錯次數還是繼續累計，每輪也固定回頭考一個，
所以這裡的字不是從此不再出現。這句要留著，不然使用者會以為掌握等於畢業。

**例句是這一頁的核心**。題庫的字大多沒有例句，只有考過並收進 words.txt 的字才有。
沒有例句的卡片會明說「還沒有例句」，不要假裝有內容。

## 十三、還沒做的功能構想

盤點過一輪全專案之後列的清單（2026-09-16），排序大致照「有趣程度」跟
「實用程度」，不是決定要做的事，是之後挑方向用的備忘：

- **發音**（已經在做，見下方「發音功能」一節）：單字/句子完全沒聲音，
  是最明顯的缺口，背錯發音是很多人的痛點。
- **`Word.imagePath` 補上圖片功能**：model 早就留了這個欄位，註解寫
  「畫面之後才做」，現在完全沒用到。圖片對記憶具象名詞（食物、動物、
  居家用品，這些都已經分類好了）幫助很大，欄位/架構都準備好了，是
  「補完已經開的坑」不是新開一個坑。
- **複習排程再聰明一點**：現在待複習的判斷是「答對/答錯次數比例」＋
  「最久沒考優先」，沒有時間衰減（間隔重複／spaced repetition，像
  SM-2 那套）。同一個字答對一次跟答對一次但隔了兩個月，現在系統是
  無感的，如果想讓複習更聰明，這是核心可以動的地方。
- **新功能的測試覆蓋率沒跟上**：`question_picker`／`spell_judge`／
  `word_status` 這些領域邏輯測得很仔細，但像單字庫標籤多選這種
  UI 層的篩選邏輯（或/且混合）完全沒有測試，之後改壞了不會有任何
  東西擋。
- 比較錦上添花的：連續天數／打卡日曆（首頁已經有每日一句鼓勵，
  加個 streak 視覺化很搭）、聽力測驗模式（聽字選意思，發音做完之後
  這個幾乎是順手的延伸）、深色／淺色主題切換（現在完全寫死深色）。

### 本地測試跟部署不要共用同一個 build 資料夾

2026-09-16 踩過的坑：本地測試用 `flutter build web`（無 base-href，根路徑），
部署 GitHub Pages 用 `flutter build web --base-href /Luma/`，兩個指令如果
都輸出到預設的 `build/web`，後建的會蓋掉先建的——本地伺服器指著
`build/web`，一旦被 `/Luma/` 版蓋過去，瀏覽器就會去找不存在的
`/Luma/manifest.json`，噴一堆 404，連 GitHub Pages 那份反而沒事。

以後兩份分開輸出，不要共用資料夾：

- `flutter build web`（本地測試，`localhost:5123` 的 `npx serve` 盯著這個）
  → 輸出到預設的 `build/web`
- `flutter build web --base-href /Luma/ -o build/web-ghpages`（部署用）
  → 輸出到 `build/web-ghpages`，複製去 gh-pages worktree 前從這裡拿

### 發音功能（2026-09-16 開始做）

用 `flutter_tts`（不是瀏覽器原生 `SpeechSynthesis`）：同一份 Dart code
在 Web／Android／iOS 都能用，背後自動接對應平台的引擎（瀏覽器
SpeechSynthesis／Android 系統 TTS／iOS AVSpeechSynthesizer）。這個專案
其實本來就是完整的 Flutter App（`android/`、`ios/` 資料夾都在），只是
目前只有部署網頁版，選 `flutter_tts` 是為了以後真的要包手機版也不用
重做這塊。

`lib/domain/services/tts_service.dart` 封裝一個 `TtsService`，固定唸
英文（`en-US`），語速用引擎預設值，沒有刻意調慢（使用者 2026-09-16 決定）。
`lib/app/providers.dart` 用 `ttsServiceProvider` 全 App 共用一個實例，
不要每個畫面各自建一個 `FlutterTts`。`SpeakerButton`
（`lib/shared/widgets/speaker_button.dart`）是唯一的發音按鈕元件，
三個地方在用：

- 單字詳情頁：標題旁邊，隨時能按。
- 測驗頁英翻中（`_TapCard`）：翻面前後都有，因為英文本來就直接顯示
  在卡片上，發音不會多洩漏什麼。
- 測驗頁中翻英拼字題（`_TypeCard`）：**判定之後才出現**，判定前故意
  不給，因為聽發音等於變相洩題（很多字聽發音就能拼出來），違背這個
  題型「不給任何提示，自己拼」的設計（見四、題型）。

### 日文軌道（2026-09-17 開始做，目前只有五十音手寫練習）

計畫是英文之外再加一個日文學習軌道，跟英文共用同一套毛玻璃介面但
配色不同。設計稿放在 `design-history/`（見下方新增的那條規則），
最後定案用「櫻」配色；日文首頁本身還沒做，目前只做出第一塊：
五十音手寫練習。

- `lib/features/kana_practice/`：`gojuon_data.dart` 是寫死的五十音清音表
  （行對假名/羅馬拼音），資料量小又幾乎不會變，不用另外做資料檔載入，
  跟 `assets/data/*.txt` 那種一直加字的題庫不是同一種東西。
  `kana_practice_page.dart` 是練習頁：選行、選字、「輔助描摹」（背景印
  淡淡的假名當參考）跟「純手寫」（空白紙）可以切換，畫布是真的能寫的
  ——`Listener` 接原始指標事件（不是 `GestureDetector` 的 `onPan*`，
  這頁如果之後又包回可捲動的容器，`GestureDetector` 會跟捲動搶手勢
  競技場，`Listener` 不進競技場、不會有這問題，所以這頁刻意整頁固定
  版面、不放進 `SingleChildScrollView`）。
- **不用手動按存，自動存**（使用者 2026-09-17 決定，取代原本的
  「儲存這張」按鈕）：換行、換字、切換輔助/純手寫模式、或離開這頁
  （包含跳去練習紀錄頁），只要紙上有墨跡就自動存一筆；按「清除重寫」
  不會存，那是使用者明確表示不想留這次嘗試。離開頁面的自動存在
  `dispose()` 裡點火就走（不能 `await`，但 repository 的寫入跟這個
  widget 的生命週期無關，銷毀了也會寫完）；用 `push` 跳去練習紀錄頁
  不會觸發 `dispose()`，這個情境額外在跳頁前手動補存一次。
- **存的是筆畫座標＋時間戳，不是圖片**（`KanaPracticeEntry.strokes`，
  `(x, y, t)`）：`x`／`y` 是**正規化座標**（紙寬／紙高的 0~1 比例，
  不是實際像素——練習當下紙的大小依螢幕寬度不同，正規化過才能保證
  同一筆紀錄無論在多大的畫布上重播、匯出都置中、填滿，不會跑位），
  `t` 是從整次練習第一次落筆算起的毫秒數，同一份紀錄所有筆畫共用
  一條時間軸，不是每筆各自從零算——這樣重播時筆畫之間停頓多久、
  每一筆寫多快，都跟當初實際寫的一致，不是用猜的固定配速交差
  （使用者 2026-09-17 要求：位置跟間隔都要對，第一版做成固定配速
  被打回票）。`KanaPracticeEntry.imageBase64` 因此變成**可以是
  null**：App 現寫存的紀錄不再存那張 PNG（有 `strokes` 就能隨時
  現畫出同樣的畫面，列表縮圖、重播都靠現算），純數字比一張 PNG
  小很多，這份紀錄現在自動存、量會越存越多，省下來的空間差很多；
  只有「匯入既有圖片」進來的紀錄才有 `imageBase64`（外部圖片沒有
  筆畫過程，只能存死圖）。
- `lib/features/kana_practice/kana_paper.dart` 集中放紙張顏色跟畫筆
  邏輯，練習頁／練習紀錄頁／匯出都共用，不要各刻一份：
  `PaperGridPainter`（格線）、`InkPainter`（畫完整筆畫，不做漸進
  顯示，練習頁現寫跟縮圖／匯出都用這個）、`ReplayInkPainter`
  （練習紀錄頁重播用，依 `elapsedMs` 對照每個點真實的 `t` 值決定
  畫到哪，包含點與點之間的線性內插，動作才會平滑不會用跳的）、
  `renderStrokesToPng`（不靠 `RepaintBoundary` 截圖——那需要紀錄
  當下真的顯示在畫面上才能截，練習紀錄頁列的是「過去」的紀錄，
  改用 `PictureRecorder` 在背景重新畫一張全新的圖，跟畫面顯示什麼
  無關，多久以前存的都能匯出）。這幾個 painter 全部認正規化座標，
  自己在 `paint(canvas, size)` 裡乘回目前的 `size`，所以同一份資料
  不管拿去畫多大都對。`ReplayInkPainter.totalDurationMs` 有測試
  （`test/features/kana_practice/replay_ink_painter_test.dart`），
  這個算錯，重播的總時長就跟著錯，是值得測的核心邏輯，不是可有
  可無的 UI 細節。
- 這頁的紙面顏色是全 App 唯一不從 `AppColors` 取色的地方（紙本來就該
  是亮色，套暗色玻璃底墨跡會看不清楚）。
- **`kana_practice_history_page.dart`：查看歷史練習、「匯入既有圖片」、
  「匯出圖片」**（使用者 2026-09-17 決定）。三種操作最後都圍著同一筆
  `KanaPracticeEntry` 轉：練習頁自動存的、這裡手動選檔案匯入的（給
  「這個功能做出來之前，已經用別的方式寫、存在電腦裡某個資料夾的
  練習圖」併進同一份紀錄用），跟點一筆紀錄之後可以「匯出圖片」存回
  真正的檔案。匯入用 `image_picker`、匯出用 `file_saver`，兩個都是
  Web／Android／iOS 同一份 API 的套件，選型理由跟 `flutter_tts` 一樣。
  匯入時圖片本身看不出寫的是哪個假名、當時有沒有開輔助描摹，用一個
  小對話框問使用者，不會用檔名去猜——檔名是使用者自己的命名習慣，
  不是穩定的資料格式，猜錯了比要求手動填一次更麻煩。

`kana-practice-files/inbox/`（repo 根目錄）放使用者手寫練習、還沒
匯入 App 的原始圖片，例如用別的方式（其他 App、手機拍照）寫好、
還沒透過「練習紀錄」頁的「匯入既有圖片」存進 App 的檔案，方便先
集中放一個地方，之後要匯入時去這裡找。**跟 `design-history/` 一樣
進版控**（使用者 2026-09-17 決定：這個 repo 有部署到公開的 GitHub
Pages，使用者知道會公開仍選擇 commit）。

**跟 `assets/` 是兩回事，絕對不要把這個資料夾加進 `pubspec.yaml`
的 `assets:` 清單**：`assets/` 底下的東西會被打包進部署的 App 本體，
這裡放的是使用者的個人練習圖片，不是題庫或設定，打包進去等於把
私人檔案塞進公開部署的網頁裡。

檔案命名格式（使用者手動命名，不是程式自動產生）：

```
YYYYMMDD[_HHmm]_<假名>_<羅馬拼音>_<hira|kata>.png
```

- 日期一定要有，時間不確定就省略（不要用「時分未知」這種字寫進
  檔名，格式對不齊，之後不好排序/搜尋）。
- `hira` / `kata` 表示平假名／片假名，不是必要語意（App 本身不看
  檔名，只是給使用者自己好認）。
- 例：`20260917_あ_a_hira.png`、`20260917_ア_a_kata.png`。

App 裡真正自動存進去的練習紀錄，存的位置是瀏覽器的 localStorage
（見「五十音手寫練習」一節），不是這個資料夾。**練習紀錄頁的
「匯出圖片」功能已經做出來了**（`file_saver`），但那只是把單一張
圖片交給瀏覽器／系統的存檔機制（Web 上通常落進下載資料夾），
App 沒辦法指定它直接寫進 repo 裡的固定路徑——如果要讓匯出的圖片
進版控，得使用者自己把下載下來的檔案搬進
`kana-practice-files/exports/`（這個子資料夾目前是空的，第一次真的
有檔案要搬進來才會建立；git 本來就不追蹤空目錄）。匯出檔名是
App 自動產生的（`savedAt` 時間戳＋假名＋羅馬拼音，例如
`20260917_1502_あ_a.png`），跟 `inbox/` 那種使用者手動命名的
`YYYYMMDD[_HHmm]_假名_羅馬拼音_hira或kata.png` 格式不同，兩邊
是分開的兩件事，不要混在一起、也不要互相套用對方的命名規則。

### YT 頻道追蹤（2026-09-22 開始做）

使用者原話：不是要照 YouTube 那樣逛訂閱的人，是訂閱太多人、想先分類，
想不知道看誰的時候能照分類找。所以這功能的核心是**分類／頻道管理**，
「看影片」是附加的，不是主功能。設計稿在
`design-history/Yt頻道訂閱管理/`（8 個版本，01～06 是探索不同版面，
07/08 是視覺精緻化，07 用香檳金、08 改貼近 YouTube 品牌紅，最後定案
接近 08 的配色）。

真的接了 YouTube Data API v3（`lib/data/services/youtube_api_service.dart`），
但因為這是純前端、部署到公開 GitHub Pages 的靜態網站，**沒有後端能藏
金鑰**，所以資料怎麼存、什麼時候打 API，是刻意分三層設計的，記錄下來
方便之後調整：

1. **長期存檔**（`YtTrackerRepository`，存瀏覽器 localStorage，也會被
   「匯出分類／頻道」帶出來、貼回 `assets/data/yt_tracker_categories.json`／
   `yt_tracker_channels.json` 進版控，跟日記/練習紀錄同一套 `seed_merge`
   機制）：
   - `YtCategory` 整筆（`id`／`name`／`color`）。
   - `YtChannel` 的大部分欄位：`name`／`categoryId`／`avatarEmoji`／
     `avatarImageUrl`／`url`／`description`／`addedAt`。這些都是使用者
     自己打的資料，不叫 API 也能用，這功能最先做出來的就是這一層
     （分類/頻道管理，不用金鑰）。

2. **第一次呼叫 API 才解析、解析完存進上面那個長期存檔（快取，之後
   不會重打）**：`YtChannel.youtubeChannelId`／`uploadsPlaylistId`。
   「依影片顯示」要抓某個頻道的影片，得先知道它「已上傳影片」那個
   播放清單的 ID，這兩個值是呼叫一次 `channels.list`（用 `forHandle`
   從頻道網址解析出的 `@handle` 去查）才拿得到的；拿到後立刻寫回
   `YtChannel` 存檔，下次同一個頻道不用再問一次——這兩個值本身不是
   敏感資料、幾乎不會變，所以可以放心跟其他頻道欄位一樣長期存、一樣
   會被匯出進 Git（使用者 2026-09-22 確認：這種東西可以直接存專案內）。
   同一次呼叫也會拿到官方頭貼網址，如果使用者自己沒貼過
   `avatarImageUrl` 就順便補上去，已經手動貼過的不會被蓋掉。

3. **「依影片顯示」（`yt_tracker_browse_page.dart`）：每次都直接問
   API、完全不落地存檔**：混合多頻道的「最新影片清單」
   （`YoutubeVideo`，標題/縮圖/發布時間），每次呼叫
   `playlistItems.list` 都是問 YouTube 當下真正的狀態，不會寫進
   localStorage 也不會匯出。頁面內部有個「同一個篩選範圍 5 分鐘內
   不重複打」的節流（`_YtTrackerBrowsePageState._ensureVideosLoaded`
   的 `_staleAfter`），純粹是為了不要每次重繪畫面都打 API，不是把
   影片清單快取起來長期使用——超過 5 分鐘、切換篩選範圍、或按「重新
   整理」都會重新問一次（2026-09-22 使用者糾正：一開始的設計沒有
   這個 5 分鐘節流，被指出「放好幾天還是同一份資料」的風險後補上）。
   **預設不抓冷藏頻道**（2026-10-12 使用者要求）：篩選範圍裡 `coldAt`
   有值的頻道不打 API；YT 設定「依影片顯示也抓冷藏頻道」打開才一起抓
   （`YtDisplayPrefs.videoIncludeCold`，跟捲動條、回到最上面同一組，跨裝置
   同步）。**待評鑑（還沒分區）的頻道也一樣預設不抓**（2026-10-14 使用者
   要求），另一個開關「依影片顯示也抓待評鑑頻道」
   （`YtDisplayPrefs.videoIncludePending`）。依頻道顯示不受影響。分類裡全是
   冷藏／待評鑑頻道時，依影片顯示改秀「這裡都是冷藏或待評鑑的頻道」＋「開設定」。
- **頻道頁搜尋**（2026-10-14，設計稿第 1 版頂部放大鏡）：只比對標題、大小寫不分。先找快取
  馬上出結果；設定「頻道搜尋也問 YouTube」（`YtDisplayPrefs.searchUseApi`，預設開）時再從
  快取記下的位置（`YtResume`）往更早翻到頻道最舊，快取已有的整段跳過、抓過的存進快取，
  整個頻道找完才說找不到；同一頻道第二次搜不再打 API。搜尋結果預設照樣列出已看過、已隱藏
  （`searchShowAll`，關掉就照篩選）。兩個設定跨裝置同步；最近搜尋也同步（2026-10-15）。

   **影片下架檢查**（2026-10-12 使用者要求）：打開頻道詳情頁時，這個頻道
   超過兩週（使用者先說一週、同天改兩週）沒查過，就背景把快取裡的影片編號丟回 YouTube 問「這些還在嗎」
   （`videos.list` 只要 `id`，50 部 1 單位；`YtRemovedVideoChecker`）。沒回
   來的＝被刪除或改成私人（分不出來），標 `YoutubeVideo.removedAt`，**快取
   不刪**；又查得到的拿掉標記。檢查不綁頁面，點進去馬上退出也會跑完。
   有下架的影片時，類型篩選多一顆「已下架 (N)」只列快取裡那些、不打 API；
   影片列縮圖蓋暗寫「已下架」，點了提示看不了。下架標記跟著快取同步，
   檢查時間只存本機（每台各自兩週查一次）。

   **抓到哪個頻道就先顯示哪個**（2026-10-12 使用者回報：一個分類五十
   個頻道要等老半天）：原本一個頻道一個頻道排隊抓、全部抓完才顯示；
   現在同時抓 6 個頻道（`_parallelChannels`，瀏覽器對同一網站本來就
   最多 6 條連線），每抓完一個頻道就把它的新影片換上去，還沒抓到的
   頻道先秀快取，膠囊上寫進度「幾／幾 個頻道」。一個頻道抓失敗只跳過
   那個頻道，全部都失敗才顯示「影片抓不下來」。每頻道抓最近 10 部；
   選「全部」時每頻道另外各抓一次 Shorts／直播清單（50 部）來貼標籤；
   時長湊滿 50 部影片才問一次。

4. **頻道詳情頁「上傳頻率」圖表：會落地快取**（`YtVideoCacheStore`，
   `lib/data/repositories/yt_video_cache_store.dart`，2026-09-23
   使用者要求）——這點刻意跟上面第 3 點的「依影片顯示」不同調，
   因為用途不一樣：圖表要抓的是近半年的完整歷史（`fetchAllVideos`
   要翻好幾頁），不是「現在有什麼新影片」，已發布影片的標題／時長／
   發布時間本來就不會變，快取起來沒有資料過期的風險。快取存在
   `yt_tracker.video_cache.<channelId>.v1`，`fetchAllVideos` 多一個
   `knownVideoIds` 參數：`playlistItems.list` 新到舊回傳，一旦某一頁
   整頁都已經在快取裡就直接停止翻頁（更舊的之前都抓過了），只有真的
   新影片才會補打一次 `fetchDurations`。效果是：頻道沒有新影片時
   重新整理這張圖，理想狀況只要 1 次 API 呼叫就能確認「跟上次一樣」，
   不用把半年份的歷史整個重抓一次。

**API 金鑰是第五種、獨立於上面四層**：放
`lib/app/providers.dart` 的 `ytApiKeyProvider`（記憶體
`StateProvider`，畫面即時反應的那份），但也會同步寫進 localStorage
（`YtApiKeyStore`，`lib/data/repositories/yt_api_key_store.dart`），
效期到「隔天 00:00」就自動失效——原本堅持完全不落地、關分頁就消失
（2026-09-22 使用者要求：「存在快取，關閉就沒了，不用長期儲存，比較
安全」），後來使用者覺得每次重新整理都要重貼太麻煩，2026-09-23 改成
現在這樣：兩邊各退一步，不用一直重貼，但也不會無限期留在瀏覽器裡。
`main()` 開機時會先讀一次本機存的金鑰（過期就當沒存過），用
`overrideWith` 灌進 `ytApiKeyProvider` 的初始值；之後存新金鑰／清除
金鑰，畫面層要自己同時呼叫 `YtApiKeyStore` 寫回本機，`ytApiKeyProvider`
本身不會自動幫你同步寫入。頁面提供 `showYtApiKeyDialog`
（`lib/features/yt_tracker/yt_api_key_dialog.dart`）統一處理輸入／
查看目前有沒有存／清除，首頁進來沒金鑰會自動跳出來問一次，但不會擋住
分類／頻道管理（只有「依影片顯示」真的需要它）。開對話框時會順便讀一次
剪貼簿，像金鑰的內容就秀「貼上並儲存」一鍵完成——這段讀取一定要在
dialog 已經開著、widget 已經 mount 之後才發起（`_YtApiKeyDialogState`
的 `initState`），不能在 `showDialog` 之前就先讀：瀏覽器讀剪貼簿常常
會跳權限詢問，要是 dialog 都還沒開，使用者按「允許」時原本那次檢查
早就判斷完「沒有候選」了，dialog 開出來什麼都不會顯示（2026-09-23
使用者實測回報過這個現象，殼一開始是先讀完剪貼簿才開 dialog，順序
反了才會這樣）。
